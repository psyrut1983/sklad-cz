# Возврат КИЗ в оборот после дистанционной продажи Wildberries

План от 09.09.2026, уточнён после анализа реального файла WB `D:/111/archive.xlsx`, обсуждения с пользователем и присланного пояснения о пакетной отправке. Основан на текущем коде проекта и официальной документации ЧЗ. Реализация начата в ветке `codex/wb-return-to-circulation`: добавлены отдельный разбор событий WB и построитель тела возврата, 16 тестов прошли. Подключение к отправке и остальные этапы ещё не завершены. По просьбе пользователя реализация приостановлена; при последнем уточнении изменён только этот план. Реальные КИЗы через API не проверялись, документы в ЧЗ не отправлялись.

## 1. Границы функции

Лёгкая промышленность (`lp`), индивидуальный читаемый КИ, ранее выведенный по причине `DISTANCE`. Оператор подтверждает фактический возврат/отказ. Требуется вернуть конкретные коды в оборот, сохранив историю их продаж. Первичный ввод, заказ кодов, импорт товаров, перемаркировка и отмена целого документа вывода в эту функцию не входят.

Наличие предыдущего вывода в местной базе не является обязательным условием. При отсутствии записи приложение проверяет код в ЧЗ под выбранным профилем и допускает возврат, если подтверждены все условия и сведения о событии WB. Местная база хранит историю и защищает от повторов; актуальное состояние кода устанавливается по ЧЗ. Проверка нужна также для кодов с местной историей: их могли обработать через ЛК или другую программу.

### Данные предоставленного образца

На листе «КИЗ» файла `archive.xlsx` (A1:J923) — 922 строки данных:

| Тип операции | Строк | Заполнены номер чека, ФН и дата | Эти реквизиты пусты |
|---|---:|---:|---:|
| Продажа | 267 | 252 | 15 |
| Возврат | 472 | 23 | 449 |
| «-» | 183 | 6 | 177 |

Это строки, а не подтверждённое количество уникальных кодов или готовых документов. КИЗ заполнен во всех строках. Столбцы: № задания, Стикер, КИЗ, Номер чека, Стоимость, Валюта, Номер фискального накопителя, Дата, Тип операции, Признак продажи юрлицу. Отдельного признака оплаты нет. Второй лист «Сборочные задания» содержит 953 строки; возможность надёжного сопоставления с ним предстоит проверить.

Числа образца не являются ограничениями приложения. Основной режим — ежедневная загрузка исходного отчёта за предыдущий день; также поддерживаются другие периоды и пересекающиеся выгрузки. Объём входного файла и число кодов в одном API-документе — разные ограничения: большой отчёт разбивается на несколько документов, а технический предел загрузки показывается отдельно.

Отсутствие чека не доказывает отсутствие оплаты. Наличие чека само по себе ещё не подтверждает, что его реквизиты подходят для документа возврата: требуется уточнить смысл полей WB. Период выгрузки указан пользователем приблизительно; не подставлять его в качестве даты события для строк с пустой датой.

Файл содержит реальные коды и данные покупателей. Для тестов создать синтетические примеры той же структуры; реальные значения не переносить в репозиторий, журналы и тестовые фикстуры.

## 2. Проверенный контракт ЧЗ

Официальный [True API](https://docs.crpt.ru/gismt/True_API/), разделы 4.1.1, 4.1.5 и справочник причин возврата:

- Создание: `POST /lk/documents/create?pg=lp`, документ `LP_RETURN`, формат `MANUAL` (JSON).
- Тело: `trade_participant_inn`, `return_type=REMOTE_SALE_RETURN`, `products_list` с полем `ki`.
- Обязателен `paid`: на документ либо на товары. Значение на товаре приоритетно.
- При `paid=true` обязательны тип, номер и дата первичного документа. При типе `OTHER` также требуется его наименование. При `paid=false` первичные реквизиты для этого сценария должны отсутствовать.
- Отправитель должен быть собственником кодов. Коды уникальны в документе, имеют статус `RETIRED`, без особого состояния. Причина возврата должна соответствовать причине выбытия; для данного приложения разрешаем только `DISTANCE`.
- Внешняя оболочка содержит Base64 тела и откреплённую подпись. Подписываем именно отправляемые данные.

Перед реализацией зафиксировать редакцию API и проверить её на целевом контуре: доступная публичная страница при исследовании индексировалась как v.649.0 от 15.04.2026. Это не гарантия последней редакции на дату внедрения.

### Уточнение по присланному пояснению

Источник обсуждения: предоставленный пользователем `pasted-text.txt`, начинающийся словами «Короткий ответ Один документ…». В тексте есть реплики «Я / Алиса», неподставленные ссылки и предположения. Рассматривать его как материал для сверки, а не как утверждённую схему API или подтверждённый ответ технической поддержки.

По [официальному True API](https://docs.crpt.ru/gismt/True_API/) подтверждены общие пределы: 30 000 кодов и 30 МБ на передаваемый документ (§1.2). Учитывать также ограничения конкретного метода. Это верхние границы, а не обязательный размер каждой пачки.

| Положение присланного текста | Решение для проекта |
|---|---|
| Несколько заказов/чеков в одном документе | Предусмотреть пакетирование; отдельный документ на каждый чек не требуется только из-за различия номера чека |
| `participant_inn`, `sntins`, предположительный `DISTANCE_RETURN` | Не применять: используем поля и причину из проверенного контракта выше |
| В примере отсутствует `paid` | Не отменяет обязательность оплаты для нашего сценария |
| Первичные реквизиты всегда общие | Для возврата допускается уровень товара; различающиеся подтверждённые реквизиты не терять при объединении |
| Номер заказа как наименование документа, дата заказа как дата документа | Автоматически не подставлять: требуется реальный первичный документ с установленными реквизитами |
| Безусловный переход на `/api/v4/true-api/…` | Не выполнять по этому тексту; отдельно проверить версию каждого метода и совместимость с текущим клиентом v3 |
| Срок «3 рабочих дня, включая дату возврата» | Не считать проверенным правилом для `lp`; подтвердить применимое основание перед реализацией контроля сроков |
| Пустые первичные поля при выводе | Отдельно проверить контракт `LK_RECEIPT`; правила вывода не переносить на возврат. Отсутствие поля, пустая строка и `null` не взаимозаменяемы |

Область задачи остаётся прежней: возврат после `DISTANCE`. Упоминание продажи по образцам в пояснении не расширяет её автоматически.

### Правила пакетирования

Сначала проверить события и допустимость операций, затем формировать документы. Один файл не обязан соответствовать одному документу, и один чек не обязан соответствовать одному документу.

- Продажи и возвраты никогда не смешивать. Профили, среды API и товарные группы разделять.
- Для `LK_RECEIPT` сохранять совместимость общих параметров, включая дату вывода; не объединять события разных дат под произвольно выбранной датой. Правила первичных реквизитов проверить отдельно.
- Для `LP_RETURN` передавать оплату и необходимые реквизиты на уровне каждой позиции. Это позволяет объединить разные заказы без подмены их данных; при необходимости интерфейс может задавать общие значения явно выбранным строкам.
- Делить совместимые позиции по настроенному размеру пачки и фактическому размеру документа. Проверять байтовый размер UTF-8, Base64 и итоговой оболочки с подписью; не путать его с количеством символов или размером XLSX. Рабочий предел выбирать консервативно в пределах API.
- Каждый сформированный документ отдельно подписывать, отправлять и учитывать по собственному ID. Получение ID ещё не подтверждает возврат кодов.
- До подтверждения показывать число документов и кодов в каждом; при ошибке одного документа не отправлять успешные повторно.

## 4. Пользовательский процесс

Профиль → загрузка исходного XLSX WB → разбор листа «КИЗ» → отдельные списки продаж, возвратов и строк без определённой операции → выбор возвратов → проверка в ЧЗ → заполнение сведений об оплате → предпросмотр → подтверждение → отправка → ожидание обработки → отчёт.

В предпросмотре показывать: строку источника, маску КИ, результат и время проверки ЧЗ, наличие местной истории, известный документ предыдущего вывода, оплату, первичный документ и причину блокировки. Для кода без истории показывать «Местная история отсутствует; проверено в ЧЗ», если проверка успешна. Отсутствие истории само по себе не блокирует возврат.

«Продажа» направляется в существующий процесс вывода, «Возврат» — в новый процесс проверки и возврата. Строки «-» не отправляются ни в один процесс, даже при наличии чека. Загрузка файла сама по себе не запускает операции. Если один код встречается в разных операциях, сначала устанавливается последовательность событий; нельзя сначала отправить все продажи, а затем все возвраты без сопоставления.

| Результат проверки ЧЗ | Решение |
|---|---|
| Уже в обороте | Пропустить отправку, сохранить факт внешней сверки |
| Выбыл по `DISTANCE`, принадлежит профилю, подходит для возврата | Допустить при проверенных сведениях WB и заполненных обязательных данных, в том числе без местной истории |
| Иная причина, другой владелец, группа или неподходящее состояние | Заблокировать с понятной причиной |
| Не найден, недостаточно сведений или ошибка API | Оставить на сверку; не считать ни выбывшим, ни находящимся в обороте |

Уже находящиеся в обороте коды показывать отдельно: «Уже в обороте, отправка не нужна». Это не результат новой успешной отправки нашего приложения.

- [ ] Обрабатывать обновление авторизации, ограничения частоты и ошибки без неконтролируемого повторения операции создания.

Результат: двойной клик, сбой сети и ошибка БД не приводят к слепой повторной отправке.

### Этап 5. Подтверждение результата и восстановление

- [ ] Опросить результат обработки именно отправленного документа от имени нужного профиля.
- [ ] Сопоставить ошибки с кодами; частичный успех фиксировать только при наличии подтверждения по конкретным кодам.
- [ ] Проверить переход кодов в состояние «В обороте»; расхождение с результатом документа оставить на сверку.
- [ ] Обновлять журнал цикла и разрешать последующий вывод только после подтверждения возврата.
- [ ] Если код уже возвращён другим способом, сохранить подтверждённое внешнее состояние и согласовать цикл с историей событий; не записывать его как успешную отправку нашего `LP_RETURN`.
- [ ] После перезапуска продолжать проверку по сохранённым ID документов.
- [ ] Сохранять связь HMAC с пакетом. При необходимости повторной проверки исходных КИ после перезапуска запрашивать повторную загрузку исходного файла и сверять HMAC; защищённое хранение исходных кодов — отдельное решение.

Результат: успех означает подтверждённый результат; закрытие браузера и перезапуск приложения не теряют журнал.

### Этап 6. Интерфейс и отчёт

- [ ] Добавить самостоятельную вкладку «Возврат в оборот».
- [ ] Для одной исходной выгрузки показать числа строк продаж, возвратов и неопределённых операций, отдельно — уникальные коды и готовые к отправке позиции.
- [ ] Показывать отсутствие местной истории как справочную информацию, а ошибки проверки ЧЗ и неопределённые события — как причины недопуска.
- [ ] Показать оплату без автоматически выбранного неподтверждённого значения; для оплаченных товаров показать поля документа.
- [ ] Перед подписью показать организацию, число кодов и сводку реквизитов.
- [ ] Показать число будущих документов и состав пачек; объяснить причину разделения (профиль, дата вывода, размер и другие общие параметры).
- [ ] Отображать раздельно: готово, заблокировано, отправлено, на обработке, возвращено, отклонено, требует сверки.
- [ ] Добавить XLSX-отчёт с результатом по строкам и ID документа; полный КИ включать только при доступном исходнике, иначе маску.
- [ ] Обновить инструкцию и API-документацию проекта.

### Этап 7. Проверки и внедрение

- [ ] Неоплаченный отказ: документ без лишних первичных реквизитов.
- [ ] Оплаченный возврат: обязательные реквизиты проверяются до отправки.
- [ ] Несколько заказов с разными чеками объединяются без потери индивидуальных реквизитов. Оплаченные и неоплаченные позиции сохраняют собственное значение оплаты и допустимый набор полей.
- [ ] Проверить границы размера пачки (N−1, N, N+1), предельное количество кодов и превышение байтового размера, включая кириллицу, экранирование и подпись.
- [ ] Проверить несколько документов из одного отчёта: отдельные ID, состояния и восстановление без повторения успешных отправок.
- [ ] Даты вывода и общие параметры продаж не подменяются ради объединения; заказ не превращается автоматически в первичный документ возврата.
- [ ] Отсутствующий чек/дата не выставляет `paid=false`; наличие чека не делает строку автоматически готовой.
- [ ] Код без местной истории при подтверждённых условиях ЧЗ и сведениях возврата допускается; при недостатке сведений — остаётся на сверке.
- [ ] Уже возвращённый через ЛК код не отправляется повторно и не учитывается как наша успешная отправка.
- [ ] Синтетический файл структуры образца: 267 продаж, 472 возврата, 183 строки «-»; все строки читаются, включая случай неверных объявленных размеров листа. Это проверка разбора, а не ожидаемое количество отправок.
- [ ] Продажа и возврат одного кода в одном файле, пересекающиеся выгрузки и возврат без даты не вызывают неверной очередности или повторной операции.
- [ ] Чужой код, иная причина выбытия, уже возвращённый код, неизвестное состояние — ожидаемая блокировка/пропуск.
- [ ] Дубликат строки, файла, события и двойной клик не создают лишнюю отправку.
- [ ] Полный цикл: продажа → возврат → продажа → возврат.
- [ ] Повтор старого отчёта после нового цикла не возвращает и не выводит код заново.
- [ ] Получение ID с последующим отклонением не считается успехом.
- [ ] Тайм-аут, сбой после отправки, перезапуск, несколько профилей и частичный результат обрабатываются корректно.
- [ ] Пройти существующие тесты вывода и новые контрактные/интеграционные тесты возврата.
- [ ] Провести сценарий на демонстрационном контуре с подходящими кодами; затем контролируемую небольшую реальную партию и сверить результат в ЛК.

## 6. Рекомендуемый порядок выпуска

1. Разбор отчёта и предпросмотр без отправки — проверить данные и бизнес-правила.
2. Журнал циклов, проверка в ЧЗ, отправка и восстановление — завершённая первая версия.
3. Удобства массовой обработки и дополнительные источники данных — после проверки реального цикла.

Критерий готовности: конкретный КИ после возврата подтверждённо находится в обороте, доступен для следующей продажи, а повторы старых событий и неопределённые ответы ЧЗ не создают повторных документов. Отсутствие местной истории не препятствует возврату, если ЧЗ и сведения события подтверждают его допустимость; неизвестная оплата и неустановленная последовательность событий не подменяются предположениями.
