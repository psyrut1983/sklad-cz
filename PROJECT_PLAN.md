## 1. Цель

Преобразовать клон приложения `sklad-cz` в простое локальное Windows-приложение для массового вывода КИЗ из оборота через API «Честного знака».

Целевой сценарий:

1. Коля запускает приложение на ноутбуке с Windows 10.
2. В браузере открывается локальный UI на `127.0.0.1`.
3. Коля выбирает профиль **«ИП Синявин»** или **«ИП Красикова»**.
4. Загружает XLSX Wildberries, относящийся целиком к выбранному профилю.
5. Приложение разбирает лист **«КИЗ»**, фильтрует строки и показывает предпросмотр.
6. После явного подтверждения приложение формирует допустимые пакеты `LK_RECEIPT`, подписывает сертификатом выбранного профиля и отправляет в ЧЗ.
7. UI показывает прогресс и итог по каждому пакету.
8. Коля скачивает XLSX-отчёт со всеми КИЗ, успешно выведенными в этой операции.
9. Приложение очищает исходный Excel и полные КИЗ, оставляя безопасную историю и данные для защиты от дублей.

Все остальные функции исходного склада удаляются после безопасной замены зависимостей.

## 2. Границы проекта

### Входит

- два изолированных профиля юрлиц;
- локальная настройка профилей через UI;
- диагностика сертификата и доступа к ЧЗ;
- загрузка и строгий разбор XLSX Wildberries;
- фильтрация, нормализация и валидация КИЗ;
- структурное извлечение 31-символьного КИ и удаление криптохвоста до показа в UI и отправки;
- предпросмотр и причины исключения строк;
- глобальная защита от повторного вывода КИЗ;
- формирование, подпись и отправка `LK_RECEIPT`;
- безопасное пакетирование;
- проверка статуса и частичный результат;
- экран результата и XLSX-отчёт;
- журнал без полных КИЗ;
- автоматические тесты;
- простой запуск на Windows 10.

### Не входит

- складской учёт, SKU и склады;
- печать этикеток и DataMatrix;
- ввод в оборот;
- обработка возвратов;
- причины вывода, отличные от дистанционной продажи;
- ТН ВЭД, баланс, SSH-синхронизация и старые бэкапы склада;
- удалённый или многопользовательский доступ;
- отдельный логин;
- хранение PIN, закрытых ключей или полных КИЗ после операции.

## 3. Зафиксированные бизнес-решения

### 3.1. Профили

- В UI ровно два профиля: **«ИП Синявин»** и **«ИП Красикова»**.
- Нейтральных названий «Юрлицо 1/2» нет.
- Один Excel целиком относится только к одному профилю.
- Профиль выбирается до загрузки и фиксируется за импортом.
- Для смены профиля текущий импорт надо сбросить и загрузить заново.
- У каждого профиля свои ИНН, отпечаток сертификата, FIAS и обязательные реквизиты ЧЗ.
- Несекретные настройки вводятся через UI и хранятся локально.
- PIN и закрытые ключи приложение не запрашивает и не хранит.
- Перед отправкой UI повторно показывает профиль, маскированный ИНН, сертификат и число КИЗ.

### 3.2. Отбор строк

- Поддерживается только причина **«Дистанционная продажа»**.
- В обработку попадают только строки `Тип операции = Продажа`.
- `Возврат`, `-` и иные значения пропускаются и показываются в сводке.
- Возвраты не реализуются, несмотря на их наличие в XLSX и старом коде.
- Строка допускается к отправке, только если заполнены `КИЗ`, `Номер чека` и `Номер фискального накопителя`.
- Дополнительно проходят проверку поля, обязательные по официальной схеме `LK_RECEIPT`.
- Каждая исключённая строка получает точную причину.

### 3.3. КИ и криптохвост

- Для лёгкой промышленности в документы ЧЗ передаётся **код идентификации (КИ) из 31 символа**: `01` + GTIN из 14 цифр + `21` + серийный номер из 13 символов.
- Полный код маркировки из XLSX может дополнительно содержать разделители и крипточасть `AI 91` + `AI 92`; эта часть в `products[].cis` не передаётся.
- `kiz_codec` извлекает КИ структурно, а не поиском первой подстроки `91` и не слепым удалением фиксированного числа последних символов.
- Допустимы два входных варианта: уже сокращённый валидный КИ из 31 символа либо полный код с валидным 31-символьным префиксом и распознанной крипточастью.
- Реальные GS/FNC1, их экранированные представления и символ `U+FFFD`, которым Wildberries заменил GS в предоставленном XLSX, нормализуются только в доказанных позициях структуры.
- Если префикс, длина, AI или границы крипточасти неоднозначны, строка отклоняется; приложение ничего не отрезает «по догадке».
- В UI, дедупликации, `LK_RECEIPT` и итоговом XLSX используется очищенный КИ из 31 символа. Исходная строка с крипточастью существует только во временной памяти активного импорта и не записывается в БД или логи.

### 3.4. Дубли

- Дубли внутри файла блокируются.
- Ранее успешно выведенный КИЗ блокируется глобально между обоими профилями.
- Если дубль найден в другом профиле, UI показывает факт и профиль предыдущей операции.
- Повторная отправка дубля в первую версию не входит.

### 3.5. Хранение данных

- Полный КИЗ существует только во время активного импорта, предпросмотра, отправки и формирования отчёта.
- После завершения, отмены или окончательной ошибки исходный Excel и полные КИЗ очищаются.
- Для истории сохраняются профиль, маска КИЗ, безопасный необратимый отпечаток, статус, `document_id`, время, число попыток и нормализованная ошибка.
- Для дедупликации используется HMAC с локальным секретом, который не попадает в Git, браузер или логи.
- Скачанный Колей XLSX является единственной долговременной копией полного списка успешно обработанных КИЗ.
- Временный отчёт выдаётся потоково либо удаляется после короткого TTL.
- После аварийного перезапуска может потребоваться повторная загрузка Excel, но слепая повторная отправка запрещена.

### 3.6. Ошибки и повторы

- HTTP 401: обновить авторизацию и повторить безопасно.
- HTTP 429: повторить с задержкой и ограничением попыток.
- Ошибка соединения до отправки тела: до трёх повторов с backoff.
- Бизнес-ошибка ЧЗ: автоматически не повторять.
- Таймаут чтения, обрыв после отправки тела или неоднозначный 5xx: статус **UNKNOWN**, без слепого повтора.
- UNKNOWN сначала сверяется по `document_id`, состоянию КИЗ либо иному подтверждённому механизму ЧЗ.
- Успешные пакеты не откатываются из-за ошибки другого пакета.

### 3.7. Реальная проверка

- До завершения кода и двух полных прогонов тестов реальные отправки запрещены.
- Затем отдельно проверяется один КИЗ **ИП Синявин** и один КИЗ **ИП Красикова**.
- Перед каждой отправкой Коля видит payload без подписи и секретов и даёт отдельное разрешение.

## 4. Доказанная структура XLSX Wildberries

Файл содержит листы **«Сборочные задания»** и **«КИЗ»**. Рабочий лист **«КИЗ»** имеет строку заголовков, 757 строк данных и колонки:

1. `№ задания`;
2. `Стикер`;
3. `КИЗ`;
4. `Номер чека`;
5. `Стоимость`;
6. `Валюта`;
7. `Номер фискального накопителя`;
8. `Дата`;
9. `Тип операции`;
10. `Признак продажи юрлицу`.

Агрегированные факты:

- `Продажа` — 219 строк;
- `Возврат` — 329;
- `-` — 209;
- у 206 продаж заполнены `Номер чека` и `Номер фискального накопителя`;
- у 13 продаж оба поля пустые — они исключаются;
- нет формул, скрытых строк/колонок, объединённых ячеек и таблиц;
- `Стоимость` бывает целой и дробной;
- все 757 значений имеют валидный по длине 31-символьный префикс `01…21…`;
- 741 значение имеет длину 85: префикс КИ из 31 символа, два разделителя, сегмент `91` + 4 символа и сегмент `92` + 44 символа;
- 16 значений уже имеют длину 31 и не содержат крипточасть;
- в XML предоставленного XLSX управляющий GS представлен символом замены `U+FFFD` на позициях 32 и 39; это особенность данного экспорта, а не разрешение считать любой `U+FFFD` разделителем.

Реальный файл не включается в Git. Кузя создаёт синтетический обезличенный XLSX с той же схемой и граничными случаями.

### 4.1. Подтверждённое правило КИ

Официальный материал сообщества «Честный знак» для лёгкой промышленности определяет КИ из 31 символа: `01` + GTIN-14 + `21` + серийный номер из 13 символов. GS1 определяет AI `01` как GTIN, AI `21` как серийный номер и требует разделитель GS/FNC1 после элемента переменной длины, если за ним идут следующие AI.

Источники:

- https://markirovka.ru/knowledge/tovarnye-gruppy/legkaya-promishlennost/sostav-koda-identifikatsii-dlya-ukazaniya-v-dokumentakh-v-razdele-markirovka-obuv
- https://www.gs1.org/standards/gs1-datamatrix-guideline/25

## 5. Доказательства из исходного кода

### Полезный контур

- `app/cz_api.py`: challenge, CAdES-BES, Windows `win32com`, Linux `pycades`, токен, статусы, `LK_RECEIPT`.
- `app/routes/import_export.py`: отправка, извлечение `document_id`, первичная проверка статуса.
- `app/utils.py`: карта `1 → lp → Лёгкая промышленность`, настройки и функции КИЗ.
- `app/routes/settings.py`: поля ЧЗ и сертификата.
- `templates/index.html`, `static/js/app.js`: примеры предпросмотра, подтверждения и результата.

### Фактический `LK_RECEIPT`

Текущий builder использует `inn`, `action = DISTANCE`, даты и реквизиты документа, `fias_id`, опциональный `buyer_inn`, `products[].cis`, цену в копейках и первичные документы. Внешний запрос содержит `document_format = MANUAL`, base64-документ, `type = LK_RECEIPT`, CAdES-BES и `pg=lp`.

### Дефекты, которые нельзя копировать

- маршрут использует данные первой позиции для всего документа;
- цена, дата и реквизиты первой позиции могут попасть ко всем КИЗ;
- builder связан с `Unit`, `SKU`, `Warehouse`;
- глобальный кэш токена не изолирован по профилям;
- UI и настройки смешаны со складскими функциями;
- лимит `/cises/info` не доказывает лимит `LK_RECEIPT`;
- нормализация меняет управляющие символы и требует характеризационных тестов.
- существующее извлечение через `split(GS)[0]` работает для настоящего GS, но не покрывает доказанный вариант Wildberries с `U+FFFD` и не валидирует 31-символьную структуру;
- вспомогательный поиск `find("91")` опасен: `91` может встретиться внутри GTIN или серийного номера и не должен считаться границей криптохвоста.

## 6. Целевая архитектура

### Backend-модули

- `app_factory` — минимальный Flask, bind только `127.0.0.1`;
- `profile_store` — два профиля и несекретные настройки;
- `excel_parser` — строгая схема XLSX;
- `selection_rules` — продажи и обязательные поля;
- `kiz_codec` — распознавание GS/FNC1/WB-разделителя, строгая проверка `01 + GTIN-14 + 21 + serial-13`, извлечение 31-символьного КИ и отказ при неоднозначности;
- `preview_service` — сводка и причины исключений;
- `dedup_store` — глобальные HMAC-отпечатки;
- `cz_auth` — подпись и отдельный токен каждого профиля;
- `lk_receipt_builder` — builder без складских моделей;
- `batch_service` — группировка и подтверждённый лимит;
- `submission_service` — отправка, повторы и UNKNOWN;
- `reconciliation_service` — сверка неоднозначного результата;
- `job_store` — импорты, пакеты, статусы и маски;
- `report_service` — XLSX и очистка.

### Минимальная модель данных

**`organization_profile`:** ID, имя, ИНН, сертификат, FIAS, API URL, `lp`, дата изменения.

**`import_job`:** ID, профиль, отпечаток файла, счётчики, статус, времена.

**`submission_batch`:** ID, job, профиль, отпечаток пакета, `PENDING/SENDING/SENT/CONFIRMED/FAILED/UNKNOWN`, `document_id`, попытки, ошибка, времена.

**`processed_kiz`:** HMAC, маска, профиль операции, статус, `document_id`, дата.

Полный КИЗ постоянно не хранится.

### UI

1. переключатель профиля;
2. карточка профиля и сертификата;
3. форма несекретных настроек;
4. «Добавить Excel»;
5. сводка: всего / продажи / пригодны / по статусу / без чека / ошибки / дубли;
6. предпросмотр;
7. «Вывести из оборота»;
8. финальное подтверждение;
9. прогресс пакетов;
10. итог по пакетам и строкам;
11. скачать XLSX;
12. предупреждение об очистке полных КИЗ.

### Поток

`Профиль → сертификат → XLSX → схема → Продажа → чек + ФН → структурное извлечение КИ-31/удаление криптохвоста → глобальные дубли → предпросмотр → подтверждение → группировка → пакеты → PENDING → подпись → отправка → document_id/UNKNOWN → сверка → XLSX → очистка`

## 10. Definition of Done

- приложение запускается на согласованной Windows/Python-среде;
- UI доступен только через `127.0.0.1`;
- профили используют только свои реквизиты, сертификат и токен;
- реальный XLSX стабильно разбирается;
- выбираются только допустимые продажи с чеком и ФН;
- полный КМ из XLSX структурно преобразуется в валидный КИ-31 до UI и `LK_RECEIPT`, а криптохвост не попадает в UI, payload, БД, журнал или логи;
- дубли блокируются глобально;
- payload каждой строки использует её данные;
- пакетирование соответствует подтверждённому лимиту;
- UNKNOWN не приводит к слепому повтору;
- по каждому пакету есть проверяемый итог;
- XLSX содержит все успешно обработанные КИЗ;
- после операции приложение не хранит полный КИЗ или исходный Excel;
- старые функции и зависимости удалены;
- тесты и повторный прогон проходят;
- по одному реальному КИЗ каждого профиля проверены;
- документация позволяет Коле самостоятельно работать.

## 11. Что потребуется от Коли позже

Не блокирует утверждение архитектуры и первые этапы, но потребуется перед production:

1. ИНН, отпечаток сертификата и FIAS **ИП Синявин**.
2. ИНН, отпечаток сертификата и FIAS **ИП Красикова**.
3. По одному допустимому тестовому КИЗ каждого профиля.
4. Отдельное разрешение перед каждой реальной отправкой.

PIN, закрытые ключи и секреты в файл и чат не передаются.

## 12. Вердикт финального аудита

- Архитектура и пользовательский поток определены.
- Формат XLSX доказательно проверен.
- Границы keep/rewrite/delete и порядок удаления определены.
- Python/CryptoPro, схема `LK_RECEIPT`, лимит и UNKNOWN оформлены техническими воротами, а не предположениями.
